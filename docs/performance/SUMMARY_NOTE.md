# FastPass 성능 재검증 요약 노트

이 문서는 [CHANGE_PLAN.md](./CHANGE_PLAN.md)와 [EXECUTION_PROMPTS.md](./EXECUTION_PROMPTS.md)의 핵심을 빠르게 확인하기 위한 요약본이다. 실제 작업과 Gate 판정은 원문을 기준으로 한다.

## 한눈에 보기

FastPass의 성능을 단순한 VU·RPS 숫자가 아니라 **재현 가능한 실행 기록, 비동기 처리 완료, 최종 DB 정합성**으로 검증한다. 안전한 실행 기반을 먼저 만들고 정합성·큐 내구성을 확인한 뒤, 승인된 격리 환경에서만 실제 부하를 측정해 검증된 결과만 포트폴리오에 반영한다.

## 핵심 원칙

- 운영 환경에는 부하 테스트를 실행하지 않는다.
- 원격 부하는 12단계에서만, 만료되지 않은 승인 manifest 범위 안에서 실행한다.
- 전용 일회성 DB·Redis와 삭제 가능한 Fixture가 확인되지 않으면 중단한다.
- VU와 RPS, HTTP `201` 접수와 DB 영속화, 정상 충돌과 시스템 오류를 구분한다.
- 큐 길이뿐 아니라 pending, in-flight, retry, DLQ와 접수·처리·DB ID 집합을 함께 감사한다.
- 같은 조건을 최소 3회 실행하고 중앙값과 범위를 사용한다.
- 비교 가능한 기준선이 없으면 개선율을 주장하지 않는다.

## 검증할 시나리오

| 시나리오 | 확인할 내용 |
| --- | --- |
| Smoke | 설정, 인증, Fixture, 결과 저장과 격리 환경 연결 |
| 단일 좌석 경쟁 | 하나의 좌석에 정확히 1건만 접수·저장되는지 |
| 50석 경쟁 | 1,000 VU가 각 1회 요청했을 때 `201=50`, `409=950`, DB 고유 좌석 50개인지 |
| 재예약 | 취소·만료 후 같은 좌석을 다시 예약하고 DB에 저장할 수 있는지 |
| VU Capacity | 동시 사용자 증가에 따른 실제 RPS, 지연, 자원 포화 변화 |
| RPS 탐색·확정 | 포화점을 찾고 지속 가능한 처리량을 동일 조건에서 재현하는지 |
| Spike | 급격한 부하 뒤 응답시간과 큐가 정상 범위로 회복되는지 |
| Soak | 60분 이상 실행에서 메모리·연결·큐 누수나 적체가 없는지 |

## 실행 순서

| 단계 | 핵심 작업 |
| --- | --- |
| 0 | 기존 원격 실행 경로와 하드코딩된 대상을 격리한다. |
| 1 | 기존 성능·정합성 주장의 근거와 현재 코드 상태를 감사한다. |
| 2 | 공통 k6 모듈, 안전한 runner와 최소 Smoke Test를 구축한다. |
| 3 | Run별 결과 저장, 큐 drain과 ID 단위 DB 감사를 구현한다. |
| 4 | 정상 충돌과 Redis·Queue·DB 장애를 구분하는 오류 계약을 확정한다. |
| 5 | 단일 좌석과 50석 경쟁 시나리오를 구현한다. |
| 6 | 취소·만료 후 재예약 회귀 테스트를 추가하고 확인된 결함만 수정한다. |
| 7 | worker 실패를 주입해 큐 유실과 재처리 내구성을 검증한다. |
| 8 | 앱·PM2·Redis·DB·큐를 같은 시간축에서 볼 수 있도록 관측성을 보강한다. |
| 9 | `ramping-vus` 기반 VU Capacity Test를 구현한다. |
| 10 | arrival-rate 기반 RPS 탐색·확정 Test를 구현한다. |
| 11 | Spike·Soak, 자동 중단 watchdog, Fixture·토큰·cleanup Runbook을 만든다. |
| 12 | 승인된 격리 환경에서 기준선과 후보를 같은 조건으로 각각 실행한다. |
| 13 | 결과를 분석해 검증된 수치만 문서와 포트폴리오에 반영한다. |

## Gate와 중단 규칙

- `STATIC_VERIFIED`: 빌드, 단위 테스트, 설정 검사와 `k6 inspect`까지 통과한 상태
- `INTEGRATION_VERIFIED`: 격리된 앱·DB·Redis에서 축소 실행과 사후 감사까지 통과한 상태
- `REMOTE_VERIFIED`: 승인된 격리 원격 환경에서 실행, watchdog, 감사와 cleanup까지 완료한 상태

필요한 Gate를 충족하지 못하면 다음 의존 단계로 넘어가지 않는다. 특히 7단계에서 메시지 유실, in-flight 관측 불가, 중복·누락 또는 처리 실패가 발견되면 `NO_GO`다. 이 상태에서는 저부하 `NON_QUALIFYING` 진단만 허용하며 처리량 확정, Spike·Soak와 포트폴리오 성과 반영은 중단한다.

## 주요 판정 기준

- 정상 예약 접수 `p95 < 200ms`, `p99 < 500ms`
- 예상하지 않은 오류율 `< 0.1%`
- 중복·유실과 처리 실패 `0건`
- DB 영속화 지연 `p95 < 2초`
- 부하 종료 후 큐 배출 `< 30초`
- RPS 확정 시 `dropped_iterations=0`이고 동일 조건을 최소 3회 재현

위 값은 1차 가설이며 실행 전에 확정한다. RPS 탐색에서 발생한 drop이나 임계값 초과는 포화점을 찾은 결과일 수 있으므로 확정 시험의 실패 기준과 혼용하지 않는다.

## 실행 산출물

모든 결과는 `k6/results/<run-id>/`에 저장한다.

- `metadata.json`: 코드·환경·부하 조건과 실행 상태
- `fixture-manifest.json`: 해당 Run이 만든 데이터와 소유 범위
- `summary.json`: k6 지표와 threshold 결과
- `consistency-audit.json`: 큐 상태와 ID 누락·초과·중복 감사
- `server-metrics.json`: 앱·DB·Redis 지표 또는 원본 위치
- `report.md`: 결과 해석, 한계와 다음 결정

기존 Run은 덮어쓰지 않으며 비밀값과 토큰 원문을 저장하지 않는다. 실행 상태와 산출물 완성 상태를 분리하고, schema·비밀·checksum 검사가 끝난 결과만 `FINALIZED`로 표시한다.

## 포트폴리오 반영 원칙

- `2,000 VU`와 `N RPS`를 별개의 실험 결과로 작성한다.
- `201`은 DB 저장 완료가 아니라 예약 접수 성공으로 표현한다.
- 모든 성능 수치에 Run ID와 결과 파일을 연결한다.
- 최고 결과 하나만 선택하지 않고 3회 결과의 중앙값과 범위를 제시한다.
- 실패한 실험, 측정 한계와 관측하지 못한 항목도 함께 기록한다.
- 동일한 인프라·Fixture·캐시·Tracing·프로필의 기준선과 후보가 있을 때만 개선율을 계산한다.

## 실행 전 최종 확인

1. 대상이 운영이 아닌 격리 환경인가?
2. 승인 manifest의 대상·한도·기간이 실제 인자와 일치하는가?
3. Fixture 용량과 토큰 TTL이 전체 실행·drain·감사를 감당하는가?
4. 오류 계약, 큐 내구성과 ID 감사가 `INTEGRATION_VERIFIED`인가?
5. 자동 중단 조건과 안전한 cleanup 방법이 준비됐는가?
6. 결과 수치를 연결할 Run ID와 필수 산출물을 보존할 수 있는가?
