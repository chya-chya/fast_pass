# FastPass 성능·동시성 현재 상태 감사

감사 기준일은 2026-09-28이며, 기준 Git HEAD는 `9bac7e71a383de859a7c6bb2cdae966a7034c66b`이다. 작업 트리에는 0단계 안전 격리 변경과 미추적 성능 문서가 있으므로 clean revision은 아니다.

이 문서는 기존 주장과 현재 저장소의 정적 증거를 대조한 결과다. 원격 API, AWS, DB, Redis에는 연결하지 않았고 부하 테스트와 네트워크 통합 테스트도 실행하지 않았다. 따라서 아래의 `verified`는 현재 코드·설정·Git 이력으로 직접 확인되는 정적 사실만 뜻하며 실제 처리 성능이나 통합 성공을 뜻하지 않는다.

## 상태 기준과 요약

- `verified`: 현재 코드·설정·Git 이력이 주장의 제한된 범위를 직접 뒷받침한다.
- `historical`: 날짜가 있는 작업 로그에 과거 실행 결과가 기록되어 있지만 원본 결과, Run ID, 정확한 Git SHA 또는 환경 정보가 없어 재현 검증할 수 없다.
- `unsupported`: 2차 문서나 예상만 있고 원본 측정값 또는 일치하는 실행 조건이 없다.
- `contradicted`: 현재 코드·스키마·실행 모델이 주장과 직접 다르거나 서로 다른 의미의 값을 같은 결과로 취급한다.

## 핵심 혼용 사항

### 3,000 VU와 3,000 RPS

현재 [`k6/load-test.js`](../../k6/load-test.js)는 `stages`를 쓰는 closed-model `ramping-vus`다. `target: 3000`은 최대 VU 설정이지만 같은 객체의 `rate: 3000`은 arrival-rate executor를 만들지 않는다. 따라서 정적으로 확인할 수 있는 사실은 “최대 3,000 VU로 구성됨”뿐이며 3,000 RPS 실행이나 달성 근거는 없다.

### HTTP 201과 DB 영속화

현재 `201`은 Redis queue push가 성공해 PENDING 객체를 반환한 시점이다. worker는 이후 `LPOP`하고 DB transaction을 수행한다. DB 실패 시 retry·DLQ 없이 메시지가 사라질 수 있으므로 `201`, processed success, DB persisted를 별도 집합으로 기록해야 한다.

### 100·500·1,000 VU 정합성 시나리오

- 날짜가 있는 작업 로그: 100 VU, 50석, HTTP 성공 50건.
- 현재 [`k6/consistency-test.js`](../../k6/consistency-test.js): 500 VU, 50석, 반복 요청, `<=50` 로그만 출력.
- ignored 포트폴리오 문서: 1,000 VU, 50석, 정확히 50건, overbooking 0건.

서로 같은 실행을 나타낸다는 근거가 없으며 어느 것도 최종 DB ID 감사를 포함하지 않는다.

## 실행 불가·오래된 설명

- README의 k6 명령은 0단계에서 루프백과 환경 ID를 요구하도록 바뀌었지만, guard는 입력된 DB/Redis 식별자가 실제 연결 대상과 일치하는지 아직 확인하지 않는다. disposable preflight 전에는 실행 근거가 부족하다.
- [`reservation.concurrency.spec.ts`](../../src/reservation/reservation.concurrency.spec.ts)는 `.env`의 영속 DB와 `REDIS_HOST` 미설정 시 `localhost:6379`를 사용하고 fixture cleanup이 없어 현재 안전 정책으로는 실행하면 안 된다.
- README와 회고의 “모든 요청 Redlock → Raw Query OCC” 흐름은 현재 “Lua hot path → Redlock cold path → Prisma updateMany worker”와 다르다.
- 회고의 “대기열 시스템 부재”는 사용자용 waiting room이 없다는 뜻으로는 유효할 수 있으나, 현재 예약 write-back용 Redis queue는 존재한다. 두 종류의 queue를 구분해야 한다.
- 로컬 Compose는 `./prometheus.yml`을 mount하지만 저장소에는 `prometheus.yml.template`만 있어 해당 파일이 별도로 없으면 그대로 실행할 수 없다.

## 즉시 보류할 주장과 다음 단계 영향

다음 표현은 새 원본 결과가 생길 때까지 성과 수치로 사용하지 않는다.

- `2,000 VU` 검증, `3,000 RPS`, DB Read `90%` 감소, RTT `100회 → 1회`.
- 500명 또는 1,000 VU에서 정합성 `100%`, overbooking·유실 `0건`.
- HTTP `201` 수를 최종 DB 예약 성공 수로 표현하는 문장.
- 같은 조건의 기준선과 후보를 비교했다는 개선율 문장.

2단계 이후에도 정적 inspect만 통과한 상태는 `STATIC_VERIFIED`다. disposable 앱·DB·Redis identity를 확인하지 못하면 기존 integration test와 k6 run을 실행하지 않는다. 특히 durable queue와 재예약 결함은 처리량 qualification 전에 별도 단계에서 검증·수정되어야 한다.
